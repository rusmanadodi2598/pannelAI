# Strict Antislop Rules: Comment and Text Hygiene

## 1. Role Definition

You are acting as a **Staff Engineer reviewing prose that a machine wrote**. Most of this repository is authored or
edited by AI coding agents, and comments are the surface where generated text shows first: correct in fact, wrong in
shape. The objective is that every comment carries information the code does not already show, and that nothing in the
tree reads as generated by habit rather than by need.

This protocol is **MANDATORY** for comments in every hand-authored file under `app-*/**`, `scrypts/**`, `docs/**` and
the root documentation. Generated output (`*_gen.go`, `*.pb.go`, `openapi.json`, `app-ui/src/lib/primitives/**`,
anything under `node_modules`) is out of scope, for the same reason AGENTS.md §1.1 exempts it: it is not hand-authored,
and splitting it is not meaningful. The panel directory is named on that list because the project already treats it as
generated in two places outside this document, `.prettierignore` ("Generated by the component layer's CLI
(`bun x shadcn-svelte add`) and not hand-edited") and `eslint.config.js`'s `ignores`, and the gate now excludes it so a
commit cannot fail over text no one wrote. One hand-written file lives inside it, `primitives/sidebar/constants.ts`,
which records a deliberate divergence from upstream and names the test that pins it, so the exclusion covers generator
output while a hand edit there stays a reviewable decision rather than a rule breach.

The filter rejects *technique without purpose*, not technique. A long comment that carries five distinct constraints is
craft; a short one that restates the line under it is noise.

## 2. Hard Rules, Machine-Enforced

Every rule here is checked by `scrypts/gates/antislop.sh`, wired into `scrypts/gates/all.sh`, CI
(`.github/workflows/gates.yml`) and the `pre-commit` hook. A rule with no check behind it is listed in §3 instead, so
the document never claims enforcement it does not have.

The repository is two halves written in two languages, and a rule that reads one of them is not the same rule as a
check that reads both, so the reach is stated per rule instead of assumed:

| Rule | `app-serv` (Go) | `app-ui` (Svelte, TypeScript) |
| --- | --- | --- |
| §2.1 dash | tree-wide, fails | tree-wide, fails |
| §2.2 separators and banners | tree-wide, fails | tree-wide, fails |
| §2.3 echo | review-only (§3) | review-only (§3) |
| §2.4 narration, end markers, emoji | tree-wide, fails | tree-wide, fails |
| §2.5 suppression states a reason | `//nolint:` without `// reason:` fails | `eslint-disable` without ` -- ` fails |
| §2.6 doc block length | fails past 16, warns past 10, on changed files | not measured, review-only (§3) |
| §2.7 §1.2 field shape | tree-wide, fails | not applicable, the panel has no §1.2 header |
| §4 scratch citations | warns on changed files | fails on changed files |

Two rows are asymmetric on purpose, and each reason lives in the section that owns the rule: §2.6 measures the shape
only where the number means something, and §4 fails where the residue is actually zero.

### 2.1 No Em Dash or En Dash (R-02)

- The characters `—` and `–` are forbidden outright in text. Use a comma, a period, a colon, a semicolon or parentheses. <!-- antislop:ignore: naming the forbidden characters is the rule, not a violation -->
- Choose by the mark's actual job: an explanation or consequence takes a colon or a new sentence, an appositive takes a
  comma, a mid-sentence aside takes parentheses. **Never substitute the character and leave the spacing behind**, which
  is how `colliding , so` reached six files in one automated sweep.
- Enforced TREE-WIDE, on every tracked text file, and it fails on any use. It used to be a changed-files check with
  `docs/**` and `AGENTS.md` excluded by name while the tree carried the legacy debt; that debt is swept, so the exclusion
  went with it instead of staying out of habit. A rule enforced only on the diff is a rule that regrows in the files
  nobody touched.

### 2.2 No Decorative Separators or ALL CAPS Banners

- A section name padded with repeated characters (`# ----- runner choice -----`, `// ========== ROUTES ==========`) is
  the pattern. Keep the label as one plain line, or drop it if it names a category nobody needs named.
- Markdown table rules (`| --- |`) are structure, not decoration, and are never flagged.

### 2.3 No Signature Echo

- A comment that repeats what the next line already shows adds reading load and no information.
  `// strPtr returns a pointer to a copy of value` above `func strPtr(value string) *string { return &value }` is the
  shape. Delete it.
- The exception is a fact the signature cannot carry: `// strPtr exists because a table row cannot take the address of a
  string literal inline` stays, because Go gives no other way to write it.

### 2.4 No Workflow Narration, End Markers, or Decorative Emoji

- `// Step 1: validate`, `// First... then... finally` narrate control flow the code already shows. If the flow is hard
  to follow, that is a structure problem, not a missing-comment problem.
- A closing brace already ends its block; `} // end if` is habit.
- Emoji used as decoration (`✅`, `🚀`, `🔒`) is visual noise and the default AI vocabulary. Write the fact in words.

### 2.5 Suppression Comments State a Constraint (AGENTS.md §1.4)

- Every `//nolint:<name>` carries `// reason: <why>` naming the constraint it protects. A bare directive with no reason
  fails the gate.
- The clause used to demand a ticket ID as well. This repository has no ticket tracker, so the ID half was
  unsatisfiable and the whole rule went unenforced; §1.4 was amended on 2026-10-05 to keep the part a machine can
  check and the part that carries information.
- The rule is about suppressions, not about Go, so it reads the panel's too: an `eslint-disable` directive carries
  its reason after ` -- `, which is eslint's own separator and what every panel directive already writes. The check
  matches only a comment that *opens* with the directive and names a plugin-qualified rule, so a sentence in
  `eslint.config.js` explaining leftover directives is not read as one. `eslint-enable` re-enables instead of
  suppressing, so it needs no reason and the check does not ask for one.

### 2.6 A Comment's Length Is Its Fact Count

- One line per irreducible fact. Past about eight lines the block is being argued rather than stated.
- The gate fails a Go doc block over 16 lines and warns past 10, measured on the block above a `func` or `type` in a
  changed file. A block that genuinely holds five constraints takes five lines; that is a pass, not a near-miss, and the
  fix is never to compress a fact into fewer words.
- A file header is not measured by total length. Once §2.7 holds, a header is eight field lines plus whatever free prose
  sits among them, so its line count says nothing; that prose is §3 material.
- The threshold is not ported to the panel, and the measurement is the reason it was not: across 567 non-test Go files,
  zero doc blocks above a `func` or `type` run past 10 lines, while the panel holds 14 declaration blocks past 10 and
  every one of them passes the fact test above. Copying "fails past 16" to `.ts` would fire first on a block carrying
  six load-bearing constraints, and the next agent reading the failure would compress facts to satisfy a number, which
  is the misuse §2.6 exists to prevent. Panel block length is therefore §3 material, named here rather than pretended
  into a gate.

### 2.7 A §1.2 Field Value Stays on One Line

- AGENTS.md §1.2 fixes the header as eight one-line fields so `@for` and `@reason` grep cleanly. A value continued on a
  second line breaks that, and gofmt makes it worse: a hand-wrapped value comes back as an indented block with empty
  comment lines around it. Before this rule existed, 1194 of 1245 Go files carried at least one wrapped field.
- The gate fails tree-wide on three shapes: an indented continuation of a field, a plain comment line directly under
  the tag, and a plain comment line after an empty one. A line opening with a lowercase letter is the rest of the
  sentence; an uppercase one continues only while the field has not finished it. A field ending with terminal
  punctuation is complete, so what follows it is a new section rather than the tail of a value, and that boundary keeps
  a stated worker decision (AGENTS.md §1.6) out of the check.
- A prose paragraph between two fields fails as well. The header is those eight fields and nothing else, so a section
  sitting among them is either the tail of the field above it, which belongs in that field, or content that belongs in
  the file body or on a declaration's own doc comment. AGENTS.md §1.6's worker statements are the common case, and they
  read better beside the code that runs them, where `go doc` also shows them.
- An indented block that follows a field which has finished its sentence is structure, not a wrapped value, and is left
  alone: 158 headers keep a runnable `go test` example exactly that way. Only a block opening in lowercase continues the
  field. The same test is in the sweep and in the gate, so the two cannot drift apart.
- A fragment that opens with a comma, semicolon or bracket attaches to the word before it. Joining with a space instead
  writes `credential , which`, which is the artifact §2.1 forbids.

## 3. Review Rules, Not Yet Machine-Checked

These need a reader. They are listed here so they are enforceable in review, and marked honestly as unautomated so no
one mistakes the document for a gate report.

- A comment earns its place by adding information the code does not show. Being true is not sufficient.
- A comment must not claim behaviour the code does not perform. This is worse than an echo and no linter catches it: a
  doc line copied across a family of constructors says what the siblings do, not what this one does. Read the body
  before repeating the sentence.
- One concise comment per logical block, not one per line.
- Sentence case, natural developer voice. "This function is responsible for validating whether the supplied credentials
  are valid" is stiff; "Validate credentials before issuing a token" is the same fact said normally.
- A TODO names an actionable task. "Future improvements" is a feeling.
- Panel comment block length is reviewed here and not measured, per §2.6: the panel's long blocks are file headers and
  fact-counted declaration docs, which is what the rule asks for, and no line count separates them from padding.
- A reference that points by coordinates is reviewed here and cannot be gated: no check can tell whether
  `EndpointKeyInput` is what a given line range used to mean. Cite the declaration instead (§4).

**Not a ban.** Never remove a comment that explains business logic and intent, an architectural decision, a security
consideration, a performance trade-off, concurrency behaviour, a protocol detail, an API contract, a workaround, an
edge case or assumption, or a licence notice. Value is not length, and the most common way this filter is misapplied
is deleting exactly these.

## 4. Citations: What May Be Referenced, and From Where

- A `draft NNN`, a `docs/DRAFT/...` path or an audit-pass reference in a comment is scratch work pointing at a document
  that closes and moves. State the fact; drop the pointer.
- Go: the gate reads only comment text below a file's `package` line, and **warns** rather than failing, because a
  commit must not be held hostage to lines its author did not write. Body-comment residue is zero. Reading comment text
  only is what makes that warning safe to promote later: the six matches an earlier run printed were all `t.Fatalf` and
  `t.Errorf` strings naming the case they assert, not comments, and the check no longer counts them.
- Panel: the gate reads only comment text, line comments and the inside of `<!-- ... -->`, and **fails**. There is no
  exempt region in TypeScript, and the residue is zero across 533 files, so a citation in a changed panel file is
  necessarily a line its author just wrote. A `draft 036` inside a test *title* is not a comment and is not reported,
  for the same reason the Go check stopped reading assertion messages.
- The same reference inside the `@reason` field of the AGENTS.md §1.2 file header is **by design**. §1.2 names that
  field as where a file's rationale lives, and 146 citations sit there legitimately. The gate ignores that region for
  this rule.
- `SPEC-API-001 §n`, `SPEC-UI §n`, `PORT nnn` and `AGENTS.md §n` pointers stay. Those name the live contract and the
  live rule, which is a reference, not a stale ticket. A pointer to a **declaration** (`EndpointKeyInput`, `IsChat`)
  also stays, and it is the form a cross-service reference should take: a symbol survives the edit that moves the lines
  under it, and `file.go:80-95` does not.

## 5. Exempting a Line

A line that quotes a violation rather than committing one may carry a trailing `antislop:ignore` marker. Every
exemption is printed when the gate runs, so an exemption stays a decision a reviewer sees. `openapi.json` is exempt as
generated output; the gate itself is exempt because its pattern constants contain the forbidden characters as data.

## 7. Where the Wider Rule Set Lives

This file states the rules **this repository enforces**. The upstream antislop skill that R-02 and its siblings come
from is a CLI-level resource installed per machine, covering interface and copy rules as well, and it is deliberately
not vendored here: a repo-committed copy would drift from a tool a developer upgrades independently. Route to it from
your own agent configuration, and treat this document as the contract for anything a gate can check.
